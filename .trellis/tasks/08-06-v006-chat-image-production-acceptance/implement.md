# 执行计划

## P0 - 基线与请求合同

- [ ] 固定 `v0.0.5` 作为不可变基线，盘点 Chat/Image 路由、provider adapter、Admin 模型目录和 BYOK 传递链。
- [ ] 建立请求矩阵：厂商、端点、模型能力、请求字段、响应类型、错误和超时。
- [ ] 检查所有外部 URL 是否被忽略，确认上游只能使用 `api.xi-ai.cn` 或后台允许配置。

Gate: 请求矩阵与实际代码路径一致，没有未识别的旁路。

## P1 - Chat 请求与流式验收

- [ ] 验证 Chat/Responses、Claude Messages、Gemini 官方端点的请求投影和响应解析。
- [ ] 验证分帧 SSE、服务端缓冲、背压、取消、超时、错误脱敏和持久化。
- [ ] 补充 provider/server/browser 回归测试。

Gate: 本地合同测试和浏览器测试能证明一次完整成功、失败、取消和重连路径。

## P2 - Image 请求与结果验收

- [ ] 验证文生图与图生图的请求格式、模型能力和参数清洗。
- [ ] 验证默认单图、真实图片字节交付、复制/下载、重试、编辑入口和错误状态。
- [ ] 验证 OpenAI/Gemini 图像模型不会误走 Chat/Responses 端点。

Gate: 图片请求响应可被浏览器展示、复制和下载，不仅返回图片地址。

## P3 - UI 与跨设备验收

- [ ] 覆盖 Chat/Image 桌面和移动端的 Key、模型、加载、失败和结果状态。
- [ ] 检查滚动所有权、弹窗、输入框、图片预览、无水平溢出和可访问名称。
- [ ] 保持本任务之外的模块不变。

Gate: 核心用户路径无阻塞性布局或交互问题。

## P4 - Docker 与运行环境

- [ ] 验证 Docker 镜像、Compose 环境变量、健康检查、`/api/health` 与 `/api/ready`。
- [ ] 验证反向代理的 SSE buffering、超时、请求体和 WebSocket/长连接相关配置。
- [ ] 使用不含真实凭据的最小 smoke，记录真实联调前提。

Gate: 服务器可以拉取固定镜像并启动到 ready，不把 Key 写入日志或文件。

## P5 - 真实联调与发布决策

- [ ] 在用户提供有效测试 Key 和可用环境后，单独执行 Chat/Image live-api smoke。
- [ ] 记录模型、端点、耗时、响应状态和脱敏错误，不记录 Key/完整提示词/图片敏感内容。
- [ ] 运行完整质量门禁并决定是否生成 `v0.0.6`。

Gate: 仅在 contract、browser、live-api、online-smoke 四类证据达到要求后发布。
